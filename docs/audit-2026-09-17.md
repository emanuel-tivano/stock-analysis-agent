## 4. Hallazgos priorizados

### HIGH — HITL obligatorio ausente

- **Evidencia:** `src/merval_agent/domain/models.py` define `PendingAction`, y README/arquitectura
  describen `PAUSED → APPROVE/MODIFY/REJECT`; `rg` no encontró endpoint, tool, repositorio ni
  lógica de continuación que lo use.
- **Impacto:** falla uno de los ocho componentes obligatorios. `CLARIFY` pide información y
  termina la ejecución; no es aprobación humana de una acción pausada.
- **Reproducción:** buscar `PendingAction`, `APPROVE`, `MODIFY`, `REJECT` en `src/` y comprobar
  que sólo aparece el modelo.
- **Recomendación:** tarea separada: definir una acción concreta, persistir su propuesta y
  estado, exponer approve/modify/reject con control de concurrencia e idempotency key, y reanudar
  desde la evidencia persistida con auditoría completa.
- **Acción:** separada; no corresponde simular cumplimiento dentro de esta auditoría.

### MEDIUM — Reproducibilidad mínima Python 3.11 no demostrada y CI ausente

- **Evidencia:** `requires-python >=3.11`; sólo está instalado Python 3.14.6. No hay workflows.
- **Impacto:** el clon funciona en un entorno limpio comprobado, pero el mínimo declarado puede
  contener incompatibilidades no observadas. Cada revisión depende de ejecución manual.
- **Reproducción:** el launcher `py`/Python 3.11 no está disponible; API de GitHub: 0 workflows.
- **Recomendación:** añadir en una tarea separada CI para 3.11 y una versión actual, con pytest,
  Ruff, smoke y build de wheel. CI es prioridad alta, aunque no requisito obligatorio del TFI.
- **Acción:** separada; no se creó CI sin poder ejecutarlo remotamente.

### MEDIUM — Evidencia real histórica no es portable

- **Evidencia:** los JSON, SQLite y logs citados por auditorías anteriores viven en
  `evals/results/`, ignorado por Git. Los enlaces rotos fueron corregidos para declararlos como
  rutas locales, pero un clon no puede auditar esas capturas.
- **Impacto:** las afirmaciones históricas pueden ser plausibles y detalladas, pero no son
  reproducibles sólo con GitHub.
- **Reproducción:** comparar links Markdown con `git ls-files`; antes de la corrección había 13

- **Recomendación:** publicar en una release o carpeta versionada resúmenes sanitizados,

## 6. Revisión técnica por área

### Agente y arquitectura

La separación `domain` / `agents` / `tools` / `adapters` / `memory` / `api` / `skills` es
coherente. `bootstrap.py` compone dependencias y permite sustituir provider, HTTP y repositorio
en tests. El dominio no importa FastAPI ni adapters. Los providers implementan la misma frontera
de decisión.

El loop no es un workflow fijo disfrazado: en cada paso entrega una copia profunda del estado y
schemas al provider, valida la decisión Pydantic y reglas de negocio, ejecuta la tool elegida y
reduce la observación. Existe presupuesto global y máximo de dos intentos por operación, con key
idempotente. Llamadas exitosas duplicadas se rechazan; sólo fallos retryable pueden repetirse.

El LLM no publica precios, métricas, suficiencia, señales, confianza ni procedencia. La respuesta
se reconstruye desde Python. Tests adversariales prueban que texto o números del provider no
alteran el reporte. El fallback determinístico queda identificado en metadata, sin atribuirse al
modelo.

La concurrencia es razonable para demo: endpoints sync se ejecutan en threadpool, el cliente
HTTP vive en lifespan y SQLite abre una conexión por escritura. No hubo prueba de carga; SQLite
no configura WAL/busy timeout, por lo que concurrencia pública intensa queda fuera del alcance.

### Análisis técnico

Producción implementa SMA20/50, EMA12/26 con seed SMA, RSI Wilder, MACD 12–26, señal 9,
histograma, variación, extremos, promedio de volumen y confirmación local. No redondea antes de
presentación. El oráculo de evaluación usa `Decimal` y pesos geométricos explícitos, sin importar
las funciones de producción.

Los tests cubren warm-up, seeds, alineación, orden, duplicados, huecos aceptados como
observaciones, cero inicial, no finitos, OHLC inválido, volumen `null`, timestamps futuros,
Buenos Aires, quote igual/posterior, moneda/instrumento, stale, filas descartadas y datos
parciales. La quote actual queda explícitamente provisional y el volumen desconocido no se
convierte en cero, según la política elegida.

Los estados `COMPLETE`, `PARTIAL`, `INSUFFICIENT_DATA`, `SOURCE_ERROR`, `STALE`,
`INVALID_DATA` y `UNVERIFIED` tienen rutas verificadas. Se conservan `BULLISH`, `BEARISH`,
`NEUTRAL` y `MIXED`. Sobrecompra/sobreventa no generan compra/venta; MACD negativo mejorando
permanece bajista relativo; contradicciones quedan visibles; confianza expresa calidad de
evidencia; no hay recomendación categórica.

### Providers y LLM

Fake es un simulador reglado y está rotulado `SIMULATED/NOT_USED`, no un modelo. Compatible y
Gemini nativo cubren JSON object/schema, objeto inválido, payload vacío, validación/reparación,
timeout, 400/401/403/429/5xx, `Retry-After`, backoff acotado, usage, costo opcional, modelo
efectivo, fallback y tracing mediante transportes simulados.

Estado actual de modelo real: `NOT_EVALUATED`. Históricamente, la documentación registra
Gemini 3.5 Flash Lite y una prueba mínima 3.6 Flash. En Fase 2, un full run quedó 14/17 y una
corrida enfocada posterior 3/3; eso no equivale a una única corrida perfecta 17/17. La V4
documenta recorridos GGAL/ALUA/YPFD/XXXX y un 503 real recuperado, pero sus archivos completos
están ignorados. No se atribuye ningún 33/33 actual a Gemini.

### Integraciones y datos

Market Tracker usa rutas documentadas, timeout, redirects controlados por cliente, validación
Pydantic, identidad ticker/mercado/moneda, normalización temporal y descarte contabilizado.
Una quote opcional fallida conserva el histórico; una quote no rejuvenece historia stale; un
fallo técnico agotado termina `ERROR`, no abstención. Quote nueva se marca provisional, conserva
timestamps/origen y tiene política `include_provisional_ohlc` o `history_only`.

Bolsar parsea HTML visible y devuelve sólo metadata documental. Listar un balance no se presenta
como extracción, ratios ni fundamentales. Las notas Murphy/Graham locales son `DEMO`, no citas
de libros. No se leen PDFs privados ni se envían automáticamente a un LLM.

### API y persistencia

`/`, `/assets`, `/health`, `/agent/run`, `/chat` y `/docs` respondieron. Pydantic limita mensaje
a 2000 y `session_id` a 100 caracteres `[A-Za-z0-9_-]`; `/chat` rechaza whitespace con 400 y
mensaje humano. JSON declara UTF-8. Errores internos de presentación reciben un trace UUID sin
exponer stack al cliente.

SQLite crea/migra aditivamente la columna `events`, usa parámetros SQL y transacción de contexto.
Persiste pedido, resumen, estado, tool trace y eventos. La lectura pública de traza omite pedido y
resumen libres. Una falla de persistencia se refleja como `PERSISTENCE_FAILURE`. No existe
snapshot completo automático, replay ni reanudación; está correctamente documentado.

### Interfaz y frontend

HTML usa landmarks, headings, label, skip link, log/status/alert y details nativos. Hay foco
visible, teclado, `prefers-reduced-motion`, breakpoints y layout sin overflow en cuatro tamaños.
La UI conserva sólo un session id opaco en `sessionStorage`; no promete memoria conversacional.

El render crea nodos con `textContent`; no usa `innerHTML` ni interpreta Markdown/HTML del
backend. Links externos se aceptan sólo `http/https`, abren con `noopener noreferrer`. La CSP,
`nosniff`, `no-referrer` y el cache explícito de assets se verifican. Los trace ids son opacos y
se muestran sólo en detalles técnicos.

No se ejecutó un lector de pantalla ni una herramienta automática WCAG. Textos extremadamente
largos se evaluaron por CSS/DOM y wrapping, pero no mediante una carga sintética de megabytes;
el backend limita la entrada y la salida está estructurada.

### Testing y evaluación

La suite aísla HTTP con `MockTransport`, SQLite con `tmp_path`, tiempos/retries con clocks
inyectados o monkeypatch y opt-ins externos mediante skips explícitos. La matriz técnica tiene
casos separados y el evaluador detecta adulteración. Los golden tests verifican resultados,
trazas y errores, no sólo status 200.

Queda deuda de frontend: no hay runner JS/E2E versionado ni chequeo automatizado de
accesibilidad/responsive. La prueba manual de esta auditoría compensa para demo, no para CI.

### Seguridad y operación

No se detectaron secretos tracked. API keys usan `SecretStr`; trazas sanitizan argumentos y
errores externos. No hay SQL dinámico con input, `eval`, `exec`, pickle ni `innerHTML` en el
runtime del producto. Las URLs de proveedores provienen de configuración local confiable, no
del request, por lo que no hay SSRF directa del usuario; en un servicio administrado deben
validarse/limitarse igualmente.

SQLite contiene pedidos libres en disco local; `.gitignore` lo excluye. Quien opere el servicio
debe tratar esa base como dato privado. `/health` prueba proceso/configuración, no disponibilidad
de downstreams, decisión adecuada para liveness pero insuficiente como readiness productiva.

### Documentación y reproducibilidad

README ahora declara integrante, problema, destinatario, flujo, arquitectura, instalación,
estado actual y limitaciones. La sección histórica continúa extensa; conviene mover hitos viejos
a docs en una futura edición docente, manteniendo un índice breve.

Una venv nueva en Python 3.14.6 instaló todas las versiones fijadas, luego la wheel sin editable.
El smoke se ejecutó desde `%TEMP%`, fuera del checkout. La wheel contiene assets y skill. No se
necesita Docker para la demo local; añadirlo no resolvería la falta de Python 3.11/CI.

## 11. Recomendación sobre fundamentales

**Es seguro comenzar el diseño acotado del análisis fundamental, pero no su implementación
integrada ni presentarlo como próxima entrega cerrada.** Primero deben cerrarse HITL y CI/Python
3.11, porque son brechas transversales y agregar otra dimensión aumentaría el costo de corregirlas.
La evidencia real portable y la licencia pueden avanzar en paralelo, pero deben cerrarse antes de
la entrega.

Contratos que deben conservarse como regresión:

- datos, metodología, señales, interpretación y limitaciones separados;
- cálculos y suficiencia exclusivamente en Python;
- LLM limitado a decisiones validadas, sin modificar cifras/estado/confianza/procedencia;
- `COMPLETE/PARTIAL/INSUFFICIENT_DATA/SOURCE_ERROR/STALE/INVALID_DATA/UNVERIFIED`;
- moneda, instrumento, período, unidad, `as_of`, `fetched_at`, fuente y hash;
- errores técnicos terminales distintos de abstención por evidencia;
- datos privados fuera del prompt salvo autorización y proyección explícita;
- fixtures Fake rotulados como simulación y evidencia real en corridas separadas;
- persistencia, idempotencia y trazabilidad por `trace_id`.

No conviene implementar RAG ni multiagente para iniciar fundamentales. Primero hace falta un
contrato de extracción/citación y un oráculo determinístico; después se decide si retrieval agrega
valor demostrado.
